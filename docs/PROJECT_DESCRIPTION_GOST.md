# Описание проекта по ГОСТ

## 1. Общие сведения

**Наименование проекта:**  
Интерактивное образовательное веб-приложение в формате визуальной новеллы  
«Пока все вместе»

**Условное наименование:**  
Пампалче

**Тип системы:**  
Интерактивное story-driven веб-приложение с образовательными модулями, игровыми механиками, системой прогресса, локальным сохранением данных и мультимедийным контентом.

**Форма реализации:**  
Одностраничное веб-приложение (SPA), предназначенное для запуска в современном браузере на персональных компьютерах, ноутбуках, планшетах и мобильных устройствах.

**Технологическая база MVP:**  
- Frontend: Angular, TypeScript
- UI: HTML, SCSS
- Формат контента: JSON
- Хранение состояния пользователя: browser local storage

## 2. Основание для разработки

Проект разработан как цифровое интерактивное приложение по мотивам образовательной платформы «Пока все вместе» с ориентацией на:
- детей 6-10 лет;
- родителей и других взрослых членов семьи;
- совместный семейный досуг;
- знакомство с семейными ценностями и культурой народа мари.

Разработка ведется как программный продукт учебно-просветительского назначения.

## 4. Назначение и цели проекта

### 4.1. Назначение

Приложение предназначено для организации совместного образовательного досуга ребенка и взрослого в игровой форме.

### 4.2. Цели создания системы

- формирование позитивного семейного взаимодействия;
- развитие интереса к чтению, обсуждению, совместному творчеству и кулинарной активности;
- знакомство с культурой народа мари;
- создание доступной цифровой образовательной среды для детей младшего школьного возраста;
- обеспечение прохождения модулей в логически выстроенном сюжетном порядке.

## 5. Характеристика объекта автоматизации

Объектом автоматизации является процесс прохождения ребенком и взрослым последовательных интерактивных образовательных модулей, объединенных единым сюжетом и персонажем-проводником Пампалче.

Система автоматизирует:
- навигацию по модулям;
- показ сцен и диалогов;
- выполнение интерактивных заданий;
- фиксацию прогресса;
- отображение наград;
- сбор пользовательских фото-результатов;
- вывод финального сертификата.

## 6. Краткое описание проекта

Приложение представляет собой визуальную новеллу с игровыми и обучающими элементами. Пользователь проходит сюжетное путешествие по четырем тематическим модулям:

1. **Литературный модуль**
2. **Сделаем вместе**
3. **Подумаем вместе**
4. **Приготовим вместе**

Прохождение организовано линейно: следующий модуль открывается только после завершения текущего.

В приложении предусмотрены:
- загрузочный экран;
- главное меню;
- карта модулей;
- экран прохождения шагов модуля;
- интерактивные задания;
- экран наград;
- финальный экран с сертификатом.

## 7. Функциональные требования

### 7.1. Требования к пользовательским функциям

Система должна обеспечивать:
- отображение стартового экрана с имитацией загрузки;
- переход в главное меню после завершения загрузки;
- запуск прохождения по кнопке начала путешествия;
- доступ к карте модулей;
- последовательное прохождение шагов в рамках модуля;
- поддержку типов шагов:
  - диалог;
  - выбор;
  - тест;
  - рефлексия;
  - видео;
  - кроссворд;
  - загрузка фото;
- локальное сохранение прогресса;
- начисление наград и искр;
- формирование локальной галереи пользовательских результатов;
- вывод финального сертификата после завершения всех модулей.

### 7.2. Требования к контенту

Контент должен храниться отдельно от программной логики и включать:
- тексты;
- названия модулей;
- описания шагов;
- параметры мини-игр;
- ссылки на изображения;
- ссылки на видео;
- награды;
- финальные тексты и условия завершения.

### 7.3. Требования к мультимедиа

Система должна поддерживать:
- иллюстрации;
- фоновые изображения;
- видеофрагменты;
- карточки-постеры;
- загружаемые пользовательские фотографии.

## 8. Нефункциональные требования

### 8.1. Требования к удобству использования

Интерфейс должен:
- быть понятным ребенку 6-10 лет;
- использовать крупные кнопки и контрастные элементы управления;
- исключать избыточную визуальную перегрузку;
- обеспечивать однозначную навигацию;
- поддерживать адаптацию под мобильные устройства и планшеты;
- отображать весь текст на русском языке корректно.

### 8.2. Требования к надежности

Система должна:
- корректно восстанавливать прогресс после перезагрузки страницы;
- устойчиво обрабатывать отсутствие загруженного пользовательского фото;
- корректно работать при неполном заполнении данных до момента подтверждения шага;
- не допускать перехода к следующему модулю без завершения текущего.

### 8.3. Требования к совместимости

Система должна работать в актуальных версиях браузеров:
- Google Chrome;
- Microsoft Edge;
- Yandex Browser;
- Safari;
- Mozilla Firefox.

### 8.4. Требования к производительности

MVP должен:
- быстро запускаться в браузере;
- не требовать серверной части для базового сценария;
- корректно загружать JSON-контент и локальные медиаресурсы;
- обеспечивать приемлемую работу на массовых устройствах.

## 9. Состав и структура системы

### 9.1. Основные подсистемы

В состав проекта входят:
- подсистема маршрутизации;
- подсистема отображения сцен и карточек шагов;
- подсистема контентной модели;
- подсистема пользовательского прогресса;
- подсистема медиаконтента;
- подсистема наград;
- подсистема финального сертификата.

### 9.2. Логическая структура

- **UI-уровень**  
  Страницы, компоненты, модальные окна, карточки шагов.

- **Уровень сценария**  
  JSON-структура модулей, шагов, наград и финального контента.

- **Уровень состояния**  
  Текущее состояние прохождения, ответы, фото, награды, открытые модули.

- **Уровень инфраструктуры**  
  Angular routing, services, local storage, загрузка ассетов.

## 10. Требования к документации

Для проекта рекомендуется формировать следующий комплект документов:

1. **Техническое задание**
2. **Описание программы**
3. **Описание применения**
4. **Руководство пользователя**
5. **Программа и методика испытаний**
6. **Ведомость эксплуатационных документов**
7. **Перечень медиаресурсов и контентных файлов**

Для MVP допустим облегченный пакет:
- ТЗ;
- архитектурное описание;
- инструкция по запуску;
- сценарное описание модулей;
- чек-лист тестирования.

## 11. Требования к испытаниям и приемке

### 11.1. Минимальные виды испытаний

Для MVP должны быть проведены:
- функциональные испытания;
- визуальная проверка интерфейса;
- проверка адаптивности;
- проверка корректности локального сохранения;
- проверка сценарной последовательности модулей;
- проверка отображения текста на русском языке;
- проверка загрузки изображений, видео и пользовательских фото.

### 11.2. Критерии приемки

Приложение считается готовым к приемке, если:
- все экраны открываются без ошибок;
- каждый модуль проходится до конца;
- следующий модуль открывается только после завершения предыдущего;
- награды начисляются корректно;
- сертификат доступен после завершения всех модулей;
- интерфейс корректно работает на мобильных и десктопных разрешениях;
- тексты отображаются без искажений кодировки.

## 12. Требования к этапам разработки

Рекомендуемая стадийность работ:

1. **Предпроектная проработка**
   - анализ концепции;
   - определение состава модулей;
   - формирование структуры контента.

2. **Проектирование**
   - разработка архитектуры;
   - разработка модели данных;
   - подготовка UI-структуры и сценариев.

3. **Реализация MVP**
   - разработка экранов;
   - подключение сценарного JSON;
   - внедрение механик заданий;
   - подключение ассетов;
   - реализация сохранений.

4. **Тестирование**
   - функциональная проверка;
   - корректировка контента и интерфейса;
   - проверка адаптивности.

5. **Подготовка к передаче**
   - оформление документации;
   - сборка финального релиза;
   - формирование комплекта исходных и эксплуатационных материалов.

## 13. Итоговое формализованное описание

Проект «Пока все вместе» является интерактивным образовательным веб-приложением в формате визуальной новеллы, предназначенным для совместного прохождения ребенком и взрослым. Система реализует последовательность сценарных модулей, объединенных единым персонажем-проводником, обеспечивает отображение мультимедийного контента, выполнение игровых и образовательных заданий, локальное сохранение прогресса и выдачу итогового сертификата.

С точки зрения документирования проект должен оформляться как программный продукт с применением требований ГОСТ 19 к программной документации и ГОСТ 34 к автоматизированным системам, в объеме, соразмерном формату MVP.
